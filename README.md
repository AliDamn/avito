# Кандидатогенерация для поиска услуг Авито

Для каждого запроса из `benchmark_queries.parquet` решение отбирает до 50 объявлений из
`benchmark_items.parquet` (~189k). Метрика — Recall@50.

**Итог на локальной валидации: Recall@50 = 0.882** (2500 отложенных групп train, собранных так,
чтобы по распределению быть похожими на бенчмарк; см. «Как проверялось качество»).

Схема решения:

```
запрос ──► e5 (дообученная) ──► иерархический индекс ──► пул ~1-5 тыс. ──► префильтр top-1000 ──► ранжировщик ──► top-50
            эмбеддинг           гео → рубрика →            объявлений        линейный скор          бустинг по 21
                                микрокатегория → лист                                               признаку
```

## Быстрый старт

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# данные соревнования: по умолчанию ~/Downloads/dataset, иначе
export AVITO_DATA_DIR=/путь/к/dataset      # train.parquet, benchmark_items.parquet, benchmark_queries.parquet

# дообученная модель -> models/e5-small-avito/   (ссылка ниже)
# кеш эмбеддингов   -> cache/                   (необязательно, ускоряет и гарантирует тот же answer.csv)

python run.py          # -> answer.csv (+ встроенная проверка формата), ~5 мин с кешем
python validate.py     # Recall@50 по шагам решения + разбор ошибок
python eda.py          # анализ данных, из которого выведены решения ниже
```

| Файл | Что делает |
|---|---|
| `run.py` | финальное решение: строит `answer.csv` и проверяет его формат |
| `validate.py` | локальная валидация, абляции по шагам, разбор ошибок |
| `eda.py` | анализ данных |
| `export_pairs.py`, `finetune_e5.py` | дообучение e5 (выгрузка пар из train, обучение на GPU) |
| `src/data.py` | загрузка данных, очистка, тексты для модели |
| `src/embed.py` | эмбеддинги локальной моделью с кешем на диск |
| `src/index.py` | иерархический индекс, признаки |
| `src/pipeline.py` | разбиение train, построение индекса, обучение ранжировщика |
| `src/ranker.py` | ранжировщик второй ступени |

## Анализ данных и выводы из него

Все цифры воспроизводятся `python eda.py`.

1. **Пропуски.** NaN только в рейтинге и числе отзывов (у объявления нет отзывов), в 35 описаниях корпуса
   (вакансии) и в одной паре координат. Пустой фильтр запроса — это пустая строка, а не NaN.
   → Тексты собираются с приведением NaN к пустой строке. Рейтинг, отзывы и договорная цена (−1/0)
   остаются NaN: бустинг обрабатывает пропуски сам, а «нет отзывов» — это информация, которую нулём не заменить.
2. **Дубли в train.** ~30.6k строк повторяют пару (группа запроса, объявление). → Удаляются, иначе
   частые пары перевешивают в статистиках гео, микрокатегорий и популярности.
3. **Сдвиг train → бенчмарк.** В бенчмарке каждый текст запроса встречается один раз, фильтр чаще пустой
   (63% против 35% в train), запросы чаще из крупных городов и регионов, тексты длиннее.
   → Валидация собирается с перевзвешиванием страт под бенчмарк (см. ниже), иначе она была бы оптимистичнее.
4. **Гео.** 17% запросов бенчмарка заданы в локации, где в корпусе нет ни одного объявления
   (регион или «вся Россия»). По train видно, куда они ведут: например, из Московской области
   в 61% случаев выбирают объявление из Москвы. → Первый уровень индекса — выученное по train
   распределение «локация поиска → локация объявления», а не точное совпадение локации.
5. **Рубрикатор.** «Вид услуги» из фильтра запроса совпадает с объявлением примерно в 98% случаев.
   Микрокатегория по тексту запроса предсказуема (у 86% запросов одна доминирующая).
   → Второй и третий уровни индекса: «Вид услуги» и микрокатегории, предсказанные по похожим запросам train.
6. **Тексты объявлений** содержат много служебного шума в параметрах (цены, график работы, «Тип стоимости…»).
   → Шум вырезается регулярками, чтобы не тратить 128 токенов модели впустую.

## Модели и алгоритмы

### 1. Эмбеддинги: `intfloat/multilingual-e5-small`, дообученная на train

- Запрос: `query: <текст> (<вид услуги из фильтра>)`. Вид услуги уточняет короткие запросы
  («баки» в «Красота, здоровье» — бакенбарды, а не топливные баки).
- Объявление: `passage: <заголовок>. <очищенные параметры>. <начало описания>`, до 400 символов.
- **Дообучение:** 200k пар «запрос → выбранное объявление» из train, 1 эпоха, батч 128,
  MultipleNegativesRankingLoss (InfoNCE, объявления других запросов батча — негативы), lr 5e-5 с разогревом
  и косинусным затуханием. Пары берутся **только из stats-части** разбиения: rank- и val-группы в обучение
  не попадают, поэтому прирост на валидации честный.
- Выбор small-версии: решение должно работать на ноутбуке (M1, 8 ГБ). Эмбеддинги корпуса считаются
  ~30 минут один раз и кешируются.

### 2. Иерархический индекс (`src/index.py`)

Вместо поиска по всем 189k объявлениям запрос спускается по дереву:

| Уровень | Узлы | Как выбираются для запроса |
|---|---|---|
| 0. Гео | локации объявлений | распределение P(локация объявления \| локация поиска) по train; берутся самые вероятные до 97% массы |
| 1. Рубрикатор | «Вид услуги» | парсинг фильтра запроса |
| 2. Микрокатегория | микрокатегории | kNN по 30 ближайшим запросам train (по эмбеддингам); точное совпадение текста весит ×3 |
| 3. Лист | объявления | ранжирование внутри выбранных узлов |

Кандидаты собираются из трёх веток: **гео** (объявления вероятных локаций), **рубрик** (объявления
4 самых вероятных микрокатегорий из любых локаций, по 500 ближайших по смыслу в каждой; это нужно для
удалённых услуг вроде «обзвона по базе») и **collab** (объявления, выбранные по похожим запросам train).

Затем **префильтр**: линейный скор `cos + Σ w·log(P_уровня + eps)` оставляет 1000 кандидатов.
Его задача — не потерять нужное объявление (полнота top-1000 = 0.968), точный порядок делает ранжировщик.

### 3. Ранжировщик (`src/ranker.py`)

`HistGradientBoostingClassifier` (sklearn) предсказывает вероятность выбора объявления по 21 признаку:
семантика (косинус, отрыв от лучшего, ранг), гео (P_geo, своя ли локация, известна ли локация, размер локации),
рубрикатор (P_mc, уверенность роутера, совпадение вида услуги), collab и популярность,
качество объявления (рейтинг, отзывы, цена, скрыт ли телефон, запрещены ли сообщения), длина запроса.

Обучается на 6000 отдельных rank-групп train. Для них признаки считаются по индексу, построенному
**без этих групп**, то есть так же «вслепую», как для тестовых запросов. Иначе collab-признак подсказывал бы
ответ, и ранжировщик выучил бы утечку. Негативы: 100 верхних по префильтру и 100 случайных.

## Как проверялось качество

`make_splits` (`src/pipeline.py`) делит train по группам запросов (текст + локация + фильтр + категория,
то есть ровно единица бенчмарка) на три непересекающиеся части:

- **stats** — по ней строятся индекс и статистики, по ней же дообучается e5;
- **rank** — 6000 групп для ранжировщика;
- **val** — 2500 групп для Recall@50.

Чтобы валидация была похожа на бенчмарк: не больше одной группы на текст запроса, группы выбираются
с весами P_бенчмарк(страта) / P_train(страта) по стратам «пустой ли фильтр × крупная локация».
Выбранные объявления val/rank добавляются в корпус бенчмарка, чтобы нужное объявление терялось среди тех же
189k «чужих», что и в настоящем тесте. `validate.py` и `run.py` используют один и тот же код пайплайна.

**Абляции — вклад каждого шага** (`python validate.py`):

| Шаг | исходная e5 | дообученная e5 |
|---|---|---|
| плоский косинус по всему корпусу | 0.400 | 0.441 |
| своя локация + косинус | 0.756 | 0.802 |
| иерархия + линейный скор, полная рубрик-ветка | 0.767 | 0.835 |
| иерархия + линейный скор, суженная рубрик-ветка | 0.768 | 0.835 |
|   └ полнота префильтра (top-1000) | 0.929 | 0.968 |
| + ранжировщик (без популярности и качества) | 0.831 | 0.880 |
| **+ популярность и качество объявления (итог)** | **0.841** | **0.882** |

Главный вклад дают иерархия (+0.37 к плоскому поиску), обученный ранжировщик вместо ручной формулы (+0.06)
и дообучение e5 (+0.04). Сужение рубрик-ветки почти не меняет качество, но в разы уменьшает пул и ускоряет поиск.

Ограничение: валидация похожа на бенчмарк по ключевым признакам, но не идентична ему, поэтому число
на платформе может отличаться от локального на несколько пунктов. Для сравнения вариантов между собой
локальной валидации достаточно, попытки на платформе на подбор не тратились.

## Найденные ошибки и что с ними сделано

**Ошибки в данных и коде по ходу работы:**
- **NaN в описаниях корпуса** (вакансии) роняли сборку текстов → все текстовые поля приводятся к строке (`data._s`).
- **Дубли пар в train** завышали статистики → удаляются при загрузке.
- **Риск утечки в ранжировщике.** Если считать признаки для обучения по индексу, в котором уже есть эти же
  запросы, collab-признак «знает» ответ. → Отдельная rank-часть и индекс без неё (предотвращено на этапе дизайна).
- **Сдвиг распределений train → бенчмарк** сделал бы случайную валидацию оптимистичной →
  стратифицированная выборка под распределение бенчмарка.
- **Рубрик-ветка тянула в пул десятки тысяч объявлений** со всей страны для популярных микрокатегорий →
  ограничение 500 ближайшими по смыслу на микрокатегорию (качество то же, пул и время меньше).
- **Ручные веса в формуле скора** давали гео-штраф на порядок больше разброса косинуса → формула оставлена
  только как префильтр, итоговый порядок учит бустинг.

**Разбор промахов итоговой модели** (последний блок вывода `validate.py`):

Из 2667 релевантных пар валидации потеряно 321 (12.0%):

| Где теряется нужное объявление | Доля от всех релевантных |
|---|---|
| не попало в пул префильтра (top-1000) | 3.2% |
| попало в пул, но ранжировщик поставил ниже top-50 | 8.8% |

| Сегмент запросов | Доля запросов | Recall@50 |
|---|---|---|
| пустой фильтр | 63.7% | 0.871 |
| фильтр задан | 36.3% | 0.901 |
| локации поиска нет в корпусе (регион, «вся Россия») | 16.7% | 0.750 |
| текст запроса встречался в train | 35.3% | 0.922 |
| нужное объявление не из локации поиска | 23.4% | 0.722 |

Выводы:
- **Основные потери — на ранжировании, а не на поиске кандидатов.** Нужное объявление почти всегда есть
  в пуле (96.8%), но среди сотен похожих объявлений той же локации и микрокатегории выбор пользователя
  предсказать трудно: тексты конкурирующих объявлений почти одинаковы, а личных предпочтений в данных нет.
- **Самый слабый сегмент — гео-переходы**: запросы из региона или «всей России» и случаи, когда пользователь
  выбрал объявление из другой локации (0.72–0.75). Здесь приходится угадывать не только услугу, но и город.
  Именно поэтому первый уровень индекса учит распределение переходов по train, а не требует совпадения
  локации (переход от «своя локация + косинус» к иерархии даёт +0.03 уже на линейном скоре).
- **Пустой фильтр хуже заданного** (0.871 против 0.901): без «Вида услуги» роутер по микрокатегориям опирается
  только на текст. В бенчмарке таких запросов большинство, поэтому валидация перевзвешена под эту долю.
- **Незнакомые тексты запросов** (не встречались в train) ранжируются хуже: для них нет точного collab-сигнала,
  работает только kNN по похожим запросам.

Что можно улучшить дальше: кросс-энкодер для переранжирования верхних 100–200 кандидатов (главный резерв —
8.8% потерь на ранжировании) и отдельная модель выбора локации объявления для региональных запросов.

**Риск переноса признака популярности.** В валидации 38% нужных объявлений встречались в train, а в корпусе
бенчмарка таких только 10%. Проверка: для 160 запросов бенчмарка, у которых в train есть тот же текст и локация,
выбранные по ним в train объявления есть в корпусе в 39% случаев против 7% для случайных объявлений тех же
локаций. Значит, сигнал на бенчмарк переносится, но его вклад может быть меньше локального. После дообучения e5
вклад признаков популярности и качества составляет всего +0.001, так что решение от него почти не зависит.

## Воспроизводимость

- Все случайности зафиксированы: разбиение (`seed=42`), выборка пар, обучение e5 и ранжировщика (`seed=0`).
- `run.py` детерминирован при тех же эмбеддингах. Эмбеддинги, посчитанные на другом железе (CUDA или CPU вместо
  Apple MPS), могут отличаться в последних знаках, и отдельные кандидаты на границе top-50 могут поменяться.
  Чтобы получить побайтово тот же `answer.csv`, положите в `cache/` выложенный кеш эмбеддингов.
- Во время инференса внешние API не вызываются: модель загружается из `models/` (исходная e5 — один раз с HuggingFace).
- Время: ~5 минут на `run.py` с кешем, ~30 минут на эмбеддинги корпуса без кеша (M1, 8 ГБ).
  Кандидаты и ранжирование для одного запроса — 30–120 мс (зависит от того, уходит ли процесс в swap на 8 ГБ).
